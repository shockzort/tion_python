сама по себе не исправит доступность соединений.

## Настройка supervision timeout действительно действует

В `deploy/ansible/provision.yml:68–81` задаётся
`[LE] ConnectionSupervisionTimeout=500` и уведомляется restart BlueZ.
На NUC значение есть в `/etc/bluetooth/main.conf`; файл изменён 14 сентября
незадолго до текущего старта daemon.

Дополнительно прочитан **контроллер**, а не только текст конфигурации:

```text
btmgmt read-sysconfig
Type: 0x001a  Length: 02  Value: f401
```

`0x01f4 = 500`, то есть default LE supervision timeout **5 секунд**.
Тип 0x001a определён в [MGMT BlueZ 5.85](https://kernel.googlesource.com/pub/scm/bluetooth/bluez.git/+/refs/tags/5.85/doc/mgmt.rst).
Возврат к старому значению 420 мс этой проверкой не подтверждается.

Это default контроллера, а не измерение negotiated timeout каждой текущей
связи. BlueZ допускает переопределение параметрами конкретного устройства;
это прямо описано в [main.conf 5.85](https://github.com/bluez/bluez/blob/5.85/src/main.conf#L211-L216).
Раздела `ConnectionParameters` в трёх прочитанных host `info` не найдено.
Пассивный захват не содержал установления/обновления соединений, поэтому
реальные текущие interval/latency/timeout из него не установлены.

Не стоит увеличивать timeout вслепую: он управляет обнаружением потери
радиоканала; ошибки жизненного цикла приложения и сопоставления ответов
таким изменением не исправляются.

## RSSI и USB-питание

Три последовательных чтения `btmgmt conn-info -t 2` дали:

| Бризер | RSSI 1 | RSSI 2 | RSSI 3 |
|---|---:|---:|---:|
| Гостиная | −88 | −86 | −88 dBm |
| Детская | −84 | −86 | −86 dBm |
| Спальня | −80 | −82 | −80 dBm |

TX power во всех снимках 7, maximum 7. Значения показывают слабый принимаемый
сигнал; сами по себе не доказывают причину прошлых разрывов. В пассивной
трёхминутной трассе гостиная имела медиану полного GET-ответа около 1.18 с,
остальные — около 0.10–0.12 с. Ни одного нового HCI-разрыва за этот период
нет. Подробности и размер выборки — [хронология](1_timeline.md).

USB AX210: `/sys/.../usb1/1-5`; `btusb.enable_autosuspend=Y`,
`power/control=auto`, `autosuspend_delay_ms=2000`. При чтении
`runtime_status=active`, накопленное время suspend 54 751 мс при активном
времени около 4 513 755 725 мс. Это не похоже на доказанный текущий цикл
засыпания; счётчики не дают времени отдельного эпизода.

`auto` разрешает runtime suspend, но не означает, что он сейчас происходит;
семантика описана в [Linux USB Power Management](https://docs.kernel.org/driver-api/usb/power-management.html).
Отключение autosuspend следует проверять отдельным сравнением при
подтверждённой корреляции suspend/resume с отказами. В ходе исследования
питание не переключалось и udev/modprobe-настройки не менялись.

## Что provisioning обеспечивает и чего не проверяет

Ansible ставит BlueZ и Docker, создаёт compose/systemd/watchdog, монтирует
host D-Bus, задаёт LE timeout. Уже есть подходящие части для этого сервиса.
Однако:

- установка `apt: state=present` не фиксирует версию BlueZ/kernel/firmware;
  при расследовании их надо записывать вместе с версией приложения;
- playbook записывает timeout, но не считывает применённое значение;
- Bluetooth-таймауты поиска/подключения/записи/ответа в основном являются
  константами Python, общей согласованной конфигурации бюджетов нет;
- readiness отдельного бризера не проверяется health endpoint;
- не включён уже существующий файловый logging на постоянном томе.

Последний пункт исправляется небольшой операционной настройкой
`EB_LOG_DIR=/app/server/data/logs` с проверкой владельца/места/ротации.
В `server/src/easy_breezy/logging.py:49–57` файловый handler уже реализован.
Другой допустимый вариант — постоянный journald logging; достаточно
выбрать один основной путь, не вводя новую систему мониторинга.
Это предложение, настройка сейчас не применялась.

## Отдельный риск: времени остановки контейнера может не хватить на cleanup

`stop_grace_period` в compose не задан, в рабочем контейнере
`Config.StopTimeout=null` и `StopSignal=""`; переопределений на хосте нет. По
[контракту Docker Compose](https://docs.docker.com/reference/compose-file/services/#stop_grace_period)
по умолчанию после 10 секунд остановки отправляется SIGKILL.
Один `BleakTransport.disconnect` у нас допускает до 10 секунд
(`ble/transport.py:143–154`), а до остановки реестра последовательно
останавливаются другие сервисы (`container.py:97–109`). Сам реестр закрывает
супервизоры параллельно (`core/registry.py:82–85`), поэтому суммировать
по 10 секунд на каждый бризер неправильно, но запаса всё равно нет.

Это подтверждённое несогласование верхних границ, **не установленный
SIGKILL во время утреннего эпизода**. Из сохранённых Docker events
за 08:00–08:20 нужные события получить не удалось. При следующей
контролируемой проверке нужны: marker завершения shutdown, причина/код
выхода контейнера и Device1 Connected после остановки приложения.
После ограничения shutdown-фаз подобрать общий grace с запасом;
одно увеличение grace не устраняет утечку частичного подключения.

## Поправки к эксплуатационной инструкции

1. **`btmgmt power` не является заведомо более полным аппаратным reset,
   чем BlueZ `Powered`.** В `docs/runbook.md:140–142,207–209` сейчас
   утверждается обратное. Но для работающей версии BlueZ оба пути
   используют `MGMT_OP_SET_POWERED`: [adapter.c](https://github.com/bluez/bluez/blob/5.85/src/adapter.c#L2978-L2988)
   и [client/mgmt.c](https://github.com/bluez/bluez/blob/5.85/client/mgmt.c#L2416-L2419).
   Высокоуровневая обработка различается, но отдельный «полный reset»
   самим выбором btmgmt не доказан. Эскалацию надо описывать по слоям:
   peer disconnect, приложение, daemon, контроллер/USB, питание устройства.

2. **Успех с другим BLE-устройством не доказывает отсутствие дефекта
   адаптера/драйвера для Tion.** Текущая формулировка `runbook.md:116–120`
   слишком категорична. Совместимость, параметры связи и firmware могут
   давать разные результаты. Контрольные опыты допустимы только со своими
   устройствами и отдельно от рабочего управления.

3. **Scan и connection не универсально несовместимы.** Возможность
   зависит от контроллера — [BleakClient](https://bleak.readthedocs.io/en/latest/api/client.html).
   Сериализация установления соединений в нашем проекте разумна, но фразу
   «нельзя одновременно» в `runbook.md:129–134` следует ограничить нашим
   проверенным режимом. Существующие соединения всё равно сосуществуют
   со сканированием Qingping; это предстоит квалифицировать на NUC.

4. **`Trusted=yes, Paired=no` само по себе не доказывает битый кэш.**
   Это разные свойства [BlueZ Device API](https://bluez.readthedocs.io/en/latest/device-api/).
   `remove` удаляет сопряжение; не делать его первым действием по одной
   комбинации флагов. Сначала сохранить состояние и определить слой отказа.

Исходный runbook оставлен без изменений: здесь сформулированы выводы
исследования, не выполненное исправление эксплуатационных процедур.
