# Qingping Air Monitor Lite CGDN1: источники и варианты подключения

Дата проверки: **2026-10-08**. Это исследование документации и открытого кода. Датчик пользователя, его прошивка и фактическая работа радио не проверялись; команды устройству не отправлялись.

## Вывод для плана

**Первым проверить получение BLE-рекламы на имеющемся сервере.** Поддержка именно CGDN1 подтверждена документацией Home Assistant, декодером `qingping-ble` и тестовыми пакетами двух идентификаторов модели. Для такого чтения не нужны Home Assistant, HomeKit pairing, облачный аккаунт и отдельный MQTT broker. [S1–S4]

Это предложение по последовательности работ, а не обещание работы любого экземпляра: перед реализацией основного пути нужен короткий эксперимент на USB-питании, а затем проверка устойчивости вместе с бризерами. Если BLE не проходит по дальности, постоянству рекламы или совместной работе адаптера, выбирать **локальный MQTT** после проверки поддержки приватизации установленной прошивкой. В MQTT потребуется самостоятельный обработчик протокола, а не только чтение плоского JSON. [S7–S10]

| Вариант | Что добавляется в систему | Условия и ограничения | Место в плане |
| --- | --- | --- | --- |
| Пассивное чтение BLE | Прием рекламы и декодирование CGDN1 | Проверить постоянство рекламы, дальность и сосуществование с соединениями Tion | Основной кандидат |
| Прямой локальный MQTT | Broker, provisioning, JSON decoder, ответы устройству и управление режимом передачи | Поддержка MQTT firmware; подтверждение обмена и восстановления после отключений | Резервный кандидат |
| HomeKit/HAP по LAN | HAP controller, pairing, обнаружение в сети и хранение pairing credentials; либо существующий HA | Поддерживающая HomeKit версия и доступный pairing code | Разумно, если HA уже используется |
| Qingping Open API / cloud push | Аккаунт, ключи API, внешний интернет, OAuth | Завязка на облако и фактический интервал отправки устройством | Не выбирать базой локальной автоматизации |

Основания сравнения: локальность BLE — [S1, S4], MQTT — [S7–S10], HAP — [S11–S13], облако — [S7, S14–S15]. Оценка сложности и приоритетов — проектное заключение.

## Что подтверждено для устройства

Официальная карточка Lite указывает температуру, влажность, CO₂, PM2.5, PM10, Wi-Fi 2,4 ГГц, Bluetooth 5.0 и питание USB-C 5 В / 1 А. Заявленные диапазоны: 0…40 °C, 0…95 %RH, 400…9999 ppm CO₂. Встроенный аккумулятор рассчитан максимум примерно на семь часов; производитель рекомендует постоянное питание. По умолчанию на батарее устройство выключается после десяти минут бездействия. Это существенно для датчика, управляющего вентиляцией. [S6]

Показания экрана, частота BLE-пакетов, частота MQTT и свежесть собственно измерения — разные вещи. Рекламное обновление каждую секунду не означает, что каждую секунду выполняется независимый замер CO₂. Для управления следует измерить фактические интервалы поступления и изменения значений. Последнее — критерий полевой проверки, а не характеристика, гарантированная найденными документами.

## BLE: данные, библиотека и настройка

### Формат и поддержка

В `qingping-ble` оба product ID `0x0E` и `0x24` соответствуют **CGDN1**. Данные находятся в `service_data` UUID `0000fdcd-0000-1000-8000-00805f9b34fb`; имя обычно `Qingping Air Monitor Lite`, но выбирать устройство только по имени не следует. [S2]

| Поле рекламы | Формат значения | Результат |
| --- | --- | --- |
| TLV `0x01`, длина 4 | `int16 LE` + `uint16 LE`, оба /10 | Температура °C и влажность % |
| TLV `0x13`, длина 2 | `uint16 LE` | CO₂, ppm |
| TLV `0x12`, длина 4 | Два `uint16 LE` | PM2.5 и PM10; за рамками первой доработки |

Декодер не требует ключа расшифровки для этих пакетов. Он не извлекает время измерения CGDN1. Поэтому для BLE следует честно хранить время приема; восстановление пропущенной истории из рекламы не предусмотрено этим форматом. [S2]

В upstream-тестах есть самостоятельные CGDN1 fixtures: ID `0x0E` дает 25,9 °C / 53,4 % / 549 ppm, ID `0x24` — 25,3 °C / 58,5 % / 609 ppm. Это подтверждает декодирование двух вариантов, но не сопоставляет их с конкретными аппаратными ревизиями или прошивками. [S3]

### Зависимости и защита свежести

Проверенная версия `qingping-ble`: **1.2.0**, опубликована 2026-09-29; commit `da63385cb7fd8ecb06323b6077d17023fa17340e`. Лицензия MIT, Python `>=3.10,<4.0`. Прямые runtime dependencies: `bluetooth-sensor-state-data`, `sensor-state-data`, `bluetooth-data-tools`. Полный сервер Home Assistant не является обязательной зависимостью. Транзитивно присутствует Bluetooth-инфраструктура, включая `habluetooth`; совместимость разрешенного набора с Python 3.12, Bleak и lockfile проекта проверяется при реализации. [S5]

**Результат `parser.update()` нельзя считать набором измерений только последнего пакета.** В проверенном `sensor-state-data` словарь `_sensor_values_updates` сохраняется между вызовами, а `_finish_update()` возвращает его в `entity_values`. Bluetooth-обертка очищает transient events, но не значения сенсоров. Например, пакет только с t/RH после полного пакета может оставить старый CO₂ в результате. [S16–S17]

Рекомендуемый контракт адаптера:

- Проверять целевой MAC, UUID, product ID и корректность структуры до обновления состояния.
- Для каждого пакета использовать новый экземпляр parser либо учитывать только реально присутствующие TLV. Второй вариант требует собственного учета наличия полей.
- Публиковать частичное обновление: только полученные сейчас величины и отдельное время свежести каждой величины. Пакет t/RH не продлевает срок свежести CO₂.
- Повтор пакета с неизменным значением сохраняет доказательство приема этого поля; неизменность числа сама по себе не означает неисправность. Запись графиков можно ограничивать отдельным интервалом.
- Не превращать поврежденный, неподдерживаемый или RSSI-only пакет в обновление измерений.

Это проектные меры, выведенные из поведения [S2, S16–S17]; их нужно подтвердить тестами адаптера.

### Практические шаги владельца

1. Зафиксировать модель на корпусе, версию firmware, используемое приложение и текущую привязку к HomeKit. Для исследования не сбрасывать устройство и не менять прошивку.
2. Подключить CGDN1 к постоянному USB-питанию. Поставить сначала рядом с сервером, затем на штатное место.
3. На сервере выполнить ограниченное сканирование в рамках существующей координации BLE. Сохранить образец `service_data`, BLE MAC, RSSI и интервалы пакетов. Не считать заранее Wi-Fi MAC из приложения равным BLE-адресу. Не выполнять GATT-pairing ради чтения рекламы.
4. Проверить наличие **всех трех** нужных величин и сопоставить с экраном. Результат, полученный только в режиме добавления устройства, недостаточен.
5. Закрыть приложение на телефоне; проверить работу при погашенном экране датчика, затем при отключенном внешнем интернете с сохраненной локальной инфраструктурой.
6. Проверить продолжительный прием на штатном месте параллельно с обычными соединениями и командами Tion. Отдельно проверить потерю USB, отключение датчика, рестарт сервиса и восстановление приема.
7. После успешной проверки зарегистрировать в Easy Breezy источник с понятным именем комнаты; включать его в правила CO₂ только после проверки индикации устаревших данных.

Это предлагаемая процедура квалификации. Home Assistant описывает пассивное чтение без облака и приблизительно ежесекундную рекламу Wi-Fi-устройств на USB; на батарее возможны редкие группы пакетов. Эти общие сведения о семействе не заменяют измерение именно экземпляра пользователя. [S1, S4]

Если рекламы нет, сначала проверить питание и режим установленной firmware. WatchFlower описывает для CGDN1 включение BLE через пункт `BLE Gateway` в Xiaomi Home; это наблюдение разработчика конкретной интеграции, а не универсальная инструкция для всех версий. Не менять существующие HomeKit/Mi Home настройки автоматически. [S18]

## Прямой MQTT: резервный путь и обязательный протокол

### Подготовка и provisioning

В модельной документации Qingping приватизация явно привязана к **MQTT firmware**. Общая инструкция требует предварительно добавить устройство в Qingping IoT и обновить firmware; процедура переключения конкретной HomeKit-версии и сохранение существующих привязок там не гарантируются. Поэтому сначала проверяется наличие штатной настройки у владельца, а изменение firmware оформляется отдельным осознанным действием. [S7–S8]

Предлагаемая процедура после подтверждения совместимости:

1. Поднять broker в LAN со стабильным адресом, отдельными учетными данными устройства и ограниченными правами на его topics.
2. Подключить датчик к Wi-Fi 2,4 ГГц; использовать Qingping IoT и аккаунт, доступный в Developer Platform.
3. Открыть `Private Config → Configurations → Add Configuration → Self-built MQTT`; указать LAN host, port, username/password, уникальный client ID, `qingping/<mac>/up` и `qingping/<mac>/down`. Для MQTT сверять идентичность по Wi-Fi MAC из payload. Передать конфигурацию устройству через платформу либо доступные Advanced settings приложения.
4. Проверить сообщения именно от устройства, ответы протокольного обработчика и правильность часов. Сам факт успешного TCP/MQTT connect недостаточен.
5. Начать с согласованных 60-секундных интервалов записи и отправки; прочитать настройки обратно и измерить фактический поток. Порт и формат адреса согласовать с поддерживаемой firmware.
6. Проверить сохранение настроек после перезагрузки и работу при отключенном WAN. Прямой адрес LAN исключает облако из маршрута данных; независимость часов, запуска и восстановления от облака еще должна быть доказана на устройстве.

Поля настройки и возможность прямого подключения описаны [S8]; путь через Advanced settings и пример topics — [S10]; версия Lite поддерживает 2,4 ГГц [S6]. Ограничения broker и порядок проверки — рекомендации для внедрения.

### Минимальный контракт обмена

В актуальной **отдельной спецификации Lite** указаны следующие сообщения. [S9]

| Направление / тип | Обработка |
| --- | --- |
| Датчик → сервер `"10"` | Ответить `"11"` с `dev_list:["FFFFFFFFFFFF"]`, если дочерних BLE-устройств нет, `code:0` и правильным текущим Unix timestamp; он используется для синхронизации часов |
| Датчик → сервер `"12"` | Текущие значения в `sensorData[]`; `temperature.value`, `humidity.value`, `co2.value`; время **каждой записи** — `timestamp.value` |
| Датчик → сервер `"17"` | История; при `need_ack:1` вернуть `"18"`, `ack_id` исходного сообщения, `code:0` и timestamp |
| Сервер → датчик `"17"` | `setting.collect_interval` и `setting.report_interval` в секундах; в документации есть пример 60/60 |
| Сервер → датчик `"12"` | Временный realtime: `up_itvl > 2` секунды, `duration` 60…3600 секунд |

Документ предупреждает, что без ответа на запрос дочерних устройств обычная отправка сенсоров может не начаться. Если выбран realtime-режим, его нужно продлевать; для постоянного минутного потока допустимо сначала квалифицировать периодические записи. Общий timestamp сообщения не заменяет время измерений. Gateway-функция описана для первого поколения; второго поколения она не касается. [S9]

Следствие для будущего адаптера: обрабатывать весь массив, проверять время и идентичность источника, устранять дубликаты, хранить позднюю историю по времени измерения. **Старую историю нельзя выдавать за новые показания для управления.** Успешный ACK означает обработку протокола, а не свежесть CO₂. Это проектные требования по формату [S9] и первичному коду [S19].

### Интервалы и неоднозначности документов

- Для Lite в коде `ha_qingping` указаны default 900 секунд и минимум 30 секунд. Это ограничение интеграции, не доказательство ограничения всех прошивок. [S20]
- Модельная облачная инструкция указывает стандартные 15 минут; ее строка о возможности изменения интервала внутренне противоречива: в колонке поддержки `No`, в описании сказано, что API позволяет менять настройку. Не обещать изменение интервала через облачный API без испытания. [S7]
- Общую таблицу приватизации с минутными интервалами нельзя переносить на CGDN1 как модельную спецификацию: отдельный JSON-протокол описывает секундные настройки. [S8–S9]

Минимум 60 секунд предлагается как исходная конфигурация эксперимента, а не подтвержденный режим экземпляра пользователя. Нельзя копировать ответы протокола только из чужого HA-компонента: проверенный coordinator обрабатывает историю `17`, а полная новая спецификация Lite содержит и другие необходимые сообщения. [S19, S9]

## HomeKit и облачные альтернативы

**HomeKit.** Производитель заявляет Apple Home для Lite. HA HomeKit Device умеет локальное подключение аксессуаров и требует pairing code и доступности устройства для нового controller. Если устройство уже сопряжено с Apple Home, перенос привязки затрагивает существующую конфигурацию; не выполнять его ради первоначальной проверки BLE. [S11–S12]

Отдельный открытый проект для **CGDN1** подтверждает чтение t/RH/CO₂ по HomeKit в LAN, но дополнительные настройки получает через закрытый Qingping cloud API и MQTT WebSocket. Наличие MQTT в таком проекте **не подтверждает прямой локальный broker**. Для Easy Breezy достаточно данных, поэтому такая зависимость от приватных облачных API не нужна. [S13]

Публичной однозначной матрицы «аппаратная ревизия × firmware × BLE / HomeKit / private MQTT» не найдено. ID `0x0E`/`0x24` нельзя автоматически объявить HomeKit/MQTT версиями. Сохранение HomeKit при приватизации остается вопросом к реальному устройству и производителю. [S2–S3, S7, S13]

**Облако.** Официальный путь: привязать датчик в Qingping+, войти тем же аккаунтом в Developer Platform, получить App Key/Secret и токен, читать список устройств/историю либо настроить push. Это отдельный канал от прямого MQTT: при cloud push публикует платформа Qingping. Для токена используется официальный Open API, а не извлечение ключа из приложения. Стандартные 15 минут и зависимость от интернета делают такой путь слабым кандидатом для локального регулирования. [S7, S14–S15]

## Что выяснить у владельца перед выбором транспорта

1. Версия firmware, регион/вариант устройства и приложение, в котором оно сейчас добавлено; используется ли Apple Home и нужно ли сохранить эту привязку?
2. Где будет датчик относительно сервера и возможно ли постоянное USB-питание? Ключевой результат затем дает измерение приема на этом месте.
3. Есть ли уже постоянно работающий Home Assistant или локальный MQTT broker? Это меняет стоимость резервного пути, но не является требованием основного BLE-варианта.

Ни один ответ не требуется, чтобы подготовить кодовый план; они нужны до окончательного выбора и полевого допуска транспорта.
