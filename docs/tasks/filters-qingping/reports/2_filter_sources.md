## Вывод

Кнопку можно встроить в существующие страницу «Устройства» и командную шину, но готовой операции сброса в проекте нет. До включения функции нужно уточнить протокол на одной поддерживаемой модели/прошивке: найденная внешняя реализация расходится с локальной спецификацией по последним двум байтам SET и ширине счетчика. Без этого «добавить один бит к нынешнему SET» — недостаточно обоснованная реализация.

На Dashboard показан **остаток ресурса фильтров в днях**, а не прошедшее время с их установки. Сброс должен восстановить ресурс по правилам устройства. Отдельная дата последней замены сейчас не хранится; вводить календарный счетчик в этот объем не требуется.

## Протокольные источники и остающиеся вопросы

Локальная спецификация помечает `resetFilterResource` как непроверенную гипотезу (`docs/protocol/tion-s4-ble.md:134`), а `sign=181` — как константу неизвестного назначения (`tion-s4-ble.md:136`). Поэтому ее текущих сведений недостаточно для приемки reset.

Первичный источник прежней реализации [TionAPI/tion_python, s4.py](https://github.com/TionAPI/tion_python/blob/master/tion_btle/s4.py) указывает в комментарии bit 7 как resetFilterResource, но сам его не выставляет; его encoder использует 181. Это подтверждение происхождения локальной гипотезы, не испытанная функция сброса.

Более подробная независимая реализация [dentra/esphome-tion, tion-api-4s-internal.h](https://github.com/dentra/esphome-tion/blob/5d1c5b4b148b1f985874b105793ba4520dc1b429/components/tion-api/tion-api-4s-internal.h#L186) описывает:

- В SET: bit 5 — factory reset, bit 6 — error reset, bit 7 — filter reset; bytes 5–6 — `uint16_t filter_time`, дни. Соседние reset-биты должны остаться нулевыми.
- В status: bytes 9–12 — work_time, 13–16 — fan_time, **17–20 — filter_time**, 21–24 — airflow_counter (`tion-api-4s-internal.h:127`). Общий тип прямо определяет `filter_time` как `uint32_t` в секундах: [tion-api-internal.h:34](https://github.com/dentra/esphome-tion/blob/5d1c5b4b148b1f985874b105793ba4520dc1b429/components/tion-api/tion-api-internal.h#L34). Локальный парсер игнорирует четвертый байт.
- Поля связи/авторежима тоже имеют семантику: байт 1 SET относится к MagicAir; это дополнительный предмет проверки сохранения режима при сервисной записи.

В [Tion4sApi::reset_filter:263](https://github.com/dentra/esphome-tion/blob/5d1c5b4b148b1f985874b105793ba4520dc1b429/components/tion-api/tion-api-4s.cpp#L263) отправляется полный текущий state с `filter_reset=true` и `filter_time=0` через STATE_SET. **Нулевое поле команды не доказывает нулевой остаток после сброса**: какое значение выбирает конкретная прошивка, в просмотренном исходнике не задано. Нельзя пока обещать 180/181/365 дней. Вывод о выборе прошивкой стандартного ресурса — рабочая гипотеза, проверяемая перечитыванием.

Все внешние ссылки проверены 2026-10-08. Ссылки dentra закреплены на текущий SHA `5d1c5b4b148b1f985874b105793ba4520dc1b429` (committer date: 2024-12-06T17:59:28Z), полученный read-only через публичный GitHub API; соответствующие raw-файлы прочитаны именно по этому SHA. Это исходники независимых проектов, а не официальная спецификация Tion. Конкретное поведение оборудования пользователя еще не проверено.

Следствия для реализации:

1. Зафиксировать новый reset payload отдельно от обычного SET; не отправлять `b5 00` с включенным bit 7 по инерции. Подтвердить значение bytes 5–6 захватом обмена при замене фильтров или испытанием на согласованном устройстве.
2. Уточнить чтение счетчика на uint32 LE (`payload[17:21]`) с минимальной длиной payload 21 байт и соответствующим fake encoder. Объем ограничить полем фильтра; остальные неизвестные поля протокола не перерабатывать.
3. Риск ширины реальный для нового ресурса свыше 194.18 дней: математически uint24 обрежет 365 дней до приблизительно 170.82. Нынешний golden с 174.46 дня этого не выявляет. **Это арифметическая демонстрация, а не наблюдение 365 дней на железе.**
4. Определить критерий результата по подтвержденному контракту конкретной прошивки: ожидаемый восстановленный диапазон секунд с допуском на время обмена, включая случай уже свежего фильтра. Просто `new > old` непригодно для повторной замены сразу после предыдущей; успешная GATT-запись не равна успешному сбросу.

## Рекомендуемое решение

### Пользовательский сценарий

Кнопка **«Смена фильтров»** в карточке бризера на вкладке «Устройства». Текст достаточно короткий, если кнопки вынести в отдельную строку действий с переносом, а выбор комнаты сделать самостоятельным на телефоне. Если понадобится меньшая ширина, допустима «Смена фильтра»; не сокращать до непонятного «Сброс».

После нажатия — подтверждение с именем устройства: «Фильтры в „Спальня“ заменены? Сбросить счетчик ресурса?» и кнопками «Отмена» / «Подтвердить». Отмена до отправки не создает команду. Во время операции подпись «Сбрасываем…», повторное нажатие заблокировано. После отправки не обещать отмену уже записанной BLE-команды. Успех: «Счетчик сброшен», затем показать перечитанный остаток; при неопределенном исходе: «Не удалось подтвердить сброс. Проверяем состояние устройства» с последующим чтением результата, без скрытого повторного reset.

Disabled: неподдерживаемая операция, нет связи, нет пригодного состояния, уже выполняется reset этого устройства. Состояние ожидания сохранять и после HTTP 202 до `command.finished` или чтения `/api/commands/{id}`. Успешный HTTP 200 сам по себе не означает `status=done`. При offline или таймауте выводить понятное локальное сообщение рядом с кнопкой, не рисовать оптимистичный новый ресурс.

На Dashboard уточнить подпись до «фильтр: осталось N дн» либо эквивалентно короткой, чтобы она не воспринималась как возраст фильтра. Точное название и размещение принять по проверке 320/360/390 px, длинных имен комнаты/устройства и масштаба текста; избежать горизонтальной прокрутки.

### Сервер и BLE

Путь: **UI → аутентифицированный REST → CommandBus → тот же воркер устройства → S4Driver под тем же локом → SET + REQUEST_PARAMS → state cache / WS / журнал → UI**.

- Выделить сервисное действие `reset_filter` (например, `POST /api/devices/{uuid}/filter/reset`) и типизированное намерение в командной шине. Не добавлять «постоянный» reset-флаг в `S4State` или климатическую `StateDelta`: действие одноразовое, не состояние и не штатная команда сценария.
- Вынести способность выполнения на сервер (`supported_actions` или `can_reset_filter`) только для проверенного S4-контракта. Наличие сканерного `model_hint` и значения БД по умолчанию недостаточно для обещания поддержки Lite/S3.
- Сохранить существующие очередь, журнал, дедупликацию, авторизацию, формат `CommandResult` и WS-события. Журналу достаточно отличать action payload от state delta; проверить совместимость чтения старых записей.
- Сервисное действие не создает и не продлевает manual-hold, не отменяет прежний hold и не останавливает управление по CO₂. Правило задается типом действия, а не ложным источником «trigger».
- Перед записью взять свежее фактическое состояние внутри сериализованной операции и сохранить power/fan/heater/temperature/mode/sound/light, а также необходимые протокольные флаги. Проверить состояние/поддержку снова в момент исполнения, не только в UI.
- Для reset отключить обычное ожидание offline-grace и автоматический повтор SET. Если устройство ушло offline между подтверждением и исполнением — вернуть ошибку; после реконнекта скрытый reset не выполняется. Для ожидания очереди установить короткий срок актуальности намерения.
- На одну подтвержденную операцию формировать один стабильный Idempotency-Key; повтор HTTP после потери ответа с тем же ключом должен вернуть существующий итог без новой BLE-записи. Блокировать второе одновременное сервисное действие для того же устройства, включая другую вкладку. Новый ключ после неопределенного исхода не создавать автоматически.
- Потеря ответа после SET требует контрольного чтения и проверки результата. Если и чтение недоступно, журнал и UI сообщают неподтвержденный исход; нельзя утверждать, что сброс не состоялся, или слепо применять обычный двухпопыточный ретрай шины. Обрыв браузера не отменяет уже принятую операцию; после возврата читать ее итог.
- Возвращать `done` только после проверки собственного постусловия reset, не опираться на обычную `_log_adjustments` для state delta. Счетчик из устройства обновляется штатной цепочкой state cache/WS; дата физической замены не выводится из результата команды.

## Порядок работ и проверка

1. **Уточнить протокол.** Зафиксировать модель/прошивку, ширину счетчика, значение reset payload, ожидаемый ресурс после операции. Сохранить захват до/после и документировать происхождение новых векторов. Нынешние golden-файлы не подгонять под код (`CLAUDE.md`); новые полученные и синтетические векторы явно различать.
2. **Кодек и драйвер.** Реализовать отдельное одноразовое reset-намерение, актуальное состояние → сохранение параметров → SET → обязательное перечитывание. Добавить проверку четвертого байта счетчика, что factory/error reset выключены, и что следующее обычное SET не повторяет filter reset.
3. **Шина и API.** Протянуть действие через текущую очередь/журнал и описанные сервисные политики. Проверить нет hold; нет отложенного reset; idempotency до/после перезапуска; недоступный/удаленный/неподдерживаемый device; 202 и последующий результат; потерянный ACK; гонку с командой fan от автоматики.
4. **UI.** Кнопка, подтверждение, cancel, disabled/pending/error/success, поддержка 202/WS/reconnect, штатное обновление Dashboard. Browser-проверка узких viewport обязательна, один лишь jsdom не доказывает вмещение.
5. **Общие проверки.** `make lint && make test`, UI-тесты по существующему скрипту проекта. Не считать fake-тест подтверждением протокола железа.
6. **Приемка на устройстве при реальной смене фильтров.** Записать до/после все управляемые поля и сырой счетчик; выполнить один reset; проверить новый ресурс, сохранность режимов и отсутствие factory reset/сброса ошибок; сверить повторным запросом, после реконнекта и перезапуска сервиса. Убедиться, что CO₂-автоматика продолжает работать и hold не появился. Проверить разные пользовательские состояния (включен/выключен) без множества бессмысленных повторных сбросов; зависимость от power зафиксировать как контракт прошивки.
